# DART QA 사람 검토 가이드

검토자는 HTML 화면 텍스트와 case 초안을 나란히 보고 각 항목을 직접 확인한다. 자동 validator의
성공은 사실 검토를 대신하지 않는다.

## 승인 체크리스트

각 case에서 다음 다섯 항목을 모두 확인한다.

1. **정답**: 질문이 요구한 값과 `expected.answer`가 정확히 같다. 쉼표, 소수점, 부호를 확인한다.
2. **기간**: 사업연도, 분기, 누적/당기 및 기준일이 질문과 답에서 일치한다.
3. **범위**: 연결/별도, 회사/부문, 계속/중단영업 등 재무 범위가 일치한다.
4. **단위**: 원, 천원, 백만원, 억원, 주, %, 배 등 표 머리글의 단위를 포함해 확인한다.
5. **근거**: 모든 인용이 현재 HTML의 화면 텍스트에 실제로 있고, 값뿐 아니라 기간·범위·항목을
   식별할 문맥을 포함한다.

하나라도 확신할 수 없으면 `decision`을 `revise`로 둔다. 추측이나 일반 지식으로 보완하지 않는다.

## Answerable 판정

- 질문에 필요한 값과 그 기간·범위·단위를 현재 HTML만으로 확정할 수 있어야 한다.
- 표의 같은 행에 여러 연도가 있으면 해당 연도 머리글을 근거에 포함한다.
- 연결과 별도 표가 함께 있으면 어떤 표인지 식별되는 제목이나 머리글을 포함한다.
- 각주가 값의 의미나 단위를 바꾸면 각주 문맥도 근거에 포함한다.
- `accepted_answers`는 표기만 다른 동일 답에 한정한다. 환산값이나 다른 단위는 추가하지 않는다.

## Unanswerable 판정

다음 중 하나라면 안전 보류 사례가 될 수 있다.

- 질문한 기간의 값이 없다.
- 값은 있지만 연결/별도 또는 회사/부문 범위를 구분할 수 없다.
- 단위가 없거나 서로 충돌해 답을 확정할 수 없다.
- 필요한 행, 열, 머리글 또는 각주가 현재 HTML에 없다.
- 여러 후보 값 중 질문과 정확히 대응하는 값을 결정할 수 없다.

문서에 답이 명확히 있는데 모델의 실패를 유도하려고 unanswerable로 표시하지 않는다.
Unanswerable의 expected 값은 `답변 보류`, 빈 accepted answers, 빈 evidence와 anchor를 사용한다.

## 가족과 split 검토

- 같은 공시의 같은 질문을 표현만 바꾼 사례는 같은 `family_id`를 사용한다.
- 같은 원본에서 만든 HTML 변형도 원본 case와 같은 family로 취급한다.
- 한 family가 development, validation, test 중 둘 이상에 들어가지 않게 한다.
- test의 정답이나 특성을 후보 생성 또는 선택에 사용하지 않는다.

## 승인 기록

- `reviewer`에 검토자를 식별할 수 있는 이름이나 조직 내 식별자를 적는다.
- `case_sha256`은 materialize가 만든 값을 유지한다. 값이 바뀌면 변경된 case를 다시 검토한다.
- 다섯 checklist 값을 실제로 확인한 뒤에만 모두 `true`로 기록한다.
- 수정이 필요하면 `decision: "revise"`와 이유를 `notes`에 적는다.
- 작성자가 직접 검토해도 되지만, 데이터셋의 한계와 이해관계가 있으면 notes에 남긴다.
